# Индивидуальная AI-выжимка проверки кошелька в Telegram

Дата: 2026-07-11

Статус: утверждённый дизайн, перед implementation plan

## Задача

Обычный итоговый отчёт Telegram сейчас похож на техническую сводку. Он
повторяет одни и те же мысли в разделах `Почему`, `Что это может значить`,
`Что делать` и `Что важно учесть`, но не объясняет простыми словами, что
система нашла у конкретного кошелька.

Нужен один короткий индивидуальный вывод. Пользователь должен понять:

- что нашли;
- почему это влияет на риск;
- чем это может быть в обычном и рискованном сценарии;
- что доказано, а что остаётся предположением;
- какую часть денег удалось проследить.

## Аудитория

Основной пользователь — человек около 40 лет, который пользуется криптовалютой
примерно год. Он знает, что такое кошелёк, перевод, биржа и USDT, но может не
знать термины `drain episode`, `anchor`, `coverage`, `source-policy`, `layering`,
`router` и внутренние названия проверок.

Поэтому обычный отчёт:

- пишет на русском языке;
- объясняет термин при первом употреблении;
- не показывает внутренние коды;
- говорит о деньгах и переводах, а не о моделях данных;
- отделяет факт от возможного объяснения.

## Решение

Использовать существующий OpenAI-compatible LLM-клиент и настроенный DeepSeek
для написания финальной выжимки. Новая зависимость не нужна.

LLM работает как редактор, а не как forensic-аналитик:

- код рассчитывает score и решение;
- код собирает подтверждённые факты и допустимые объяснения;
- LLM выбирает главное и пишет 2–3 коротких абзаца;
- код проверяет ответ;
- при любой ошибке используется короткий детерминированный fallback.

LLM не может изменить score, решение, coverage или доказательную силу сигнала.

## Когда вызывается LLM

LLM вызывается один раз, когда завершены Where Is Money и DeepCheck и доступен
единый финальный результат.

Предварительный ответ не содержит score и причин:

```text
Откуда деньги готово. DeepCheck ещё работает.
Финальный отчёт придёт после завершения.
```

Если итогового решения нет, LLM не вызывается. Бот пишет причину простым
детерминированным текстом:

```text
Итоговый риск не рассчитан: не загрузилась часть истории переводов.
Не считать адрес чистым или рискованным до повторной проверки.
```

## Детерминированная часть сообщения

Код, а не LLM, выводит:

- заголовок;
- проверяемый адрес;
- цветной индикатор риска;
- score и уровень;
- финальное решение.

Пример:

```text
Проверка адреса

TGytcHDm9k4r6QPvine8c6A3WWaqTBZAZD
🟠 78/100 — высокий риск. Не принимать автоматически.
```

После этого код добавляет проверенные AI-абзацы.

## Входные данные для LLM

LLM не получает полный raw JSON, сырые provider payload, chat id, Telegram id,
API-ключи или внутренние ошибки.

Сборщик создаёт компактный `WalletNarrativeCase`:

```ts
type WalletNarrativeCase = {
  locale: "ru" | "en";
  audience: "crypto_beginner";
  decision: "DECLINE" | "REVIEW" | "ACCEPTABLE";
  score: number;
  level: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL";
  checkedAddress: string;
  checkedTransferCount: number | null;
  tracedAmountPercent: number | null;
  untracedAmountPercent: number | null;
  coverageExplanation: {
    reasonKind: string;
    userText: string;
    isRiskEvidence: false;
  } | null;
  facts: NarrativeFact[];
};

type NarrativeFact = {
  evidenceId: string;
  kind: string;
  importance: number;
  proofStrength: "exact" | "strong" | "context" | "limitation";
  statement: string;
  addresses: string[];
  percentages: number[];
  amounts: string[];
  allowedInterpretations: string[];
  requiredCaveat: string | null;
};
```

`statement`, `allowedInterpretations` и `requiredCaveat` создаёт код по
структурированным полям отчёта. LLM не придумывает список сценариев с нуля.

## Факт, возможный смысл и граница знания

Для каждого существенного сигнала код передаёт три части:

1. подтверждённый факт;
2. допустимые обычный и рискованный сценарии;
3. что нельзя доказать по доступным данным.

Пример для bridge:

- факт: `83% проверяемой суммы связано с UsdtOFT; 10 путей`;
- обычный сценарий: обмен токена или перевод активов в другую сеть;
- рискованный сценарий: попытка разорвать публично видимую цепочку
  происхождения средств;
- граница знания: bridge сам по себе не доказывает отмывание.

## Когда можно упоминать возможное отмывание

Одна сервисная граница недостаточна. Сценарий сокрытия происхождения или
отмывания разрешено упоминать только при дополнительном структурированном
сигнале:

- большая доля проверяемой суммы проходит через маршрут;
- маршрут повторяется;
- деньги быстро уходят дальше;
- сумма хорошо сохраняется между переводами;
- несколько независимых фактов указывают на транзитный маршрут.

Код определяет наличие этих сигналов. LLM только объясняет их.

Если сценарий отмывания упомянут, тот же абзац обязан:

- назвать правдоподобный обычный сценарий;
- написать, что текущие данные не доказывают отмывание.

Если есть exact approval-drain, active USDT blacklist или другое точное hard
evidence, LLM пишет доказанный факт прямо и не размывает его альтернативными
версиями.

## Понятное объяснение покрытия

В обычном тексте запрещены слова:

- `drain episode`;
- `anchor coverage`;
- `coverage ratio`;
- `checked scope`;
- `partial provenance`.

Coverage объясняется через проверяемую сумму:

```text
Мы проследили происхождение 83% проверяемой суммы.
Оставшиеся 17% не удалось проследить по доступной истории переводов.
```

Если полезно количество переводов, оно показывается отдельно:

```text
Мы проверили 10 входящих переводов и проследили происхождение 83% суммы.
```

Количество переводов нельзя использовать как замену доле суммы. Например,
`10 переводов` и `83% суммы` не означают `8 из 10 переводов`.

Само покрытие не является признаком риска. Оно показывает, насколько полно
система видит происхождение проверяемых денег.

### Почему часть суммы не прослежена

Если происхождение части суммы не установлено, бот обязан назвать техническую
причину. Общая фраза `не удалось проследить` без объяснения запрещена.

Код переводит структурированный stop reason в понятный текст:

| Техническая причина | Текст для пользователя |
|---|---|
| лимит запросов или graph budget | `Проверка достигла лимита загрузки истории раньше, чем нашла источник оставшейся суммы.` |
| provider cap или неполный ответ | `Источник данных не отдал более старые переводы, поэтому часть суммы осталась без установленного источника.` |
| история ещё не проиндексирована | `Система ещё не загрузила нужный участок истории переводов.` |
| сервисная граница | `Деньги дошли до биржи или моста. После такой точки публичная цепочка не показывает, от какого клиента сервиса они пришли.` |
| слабая связь суммы и времени | `Система нашла более ранние переводы, но не смогла надёжно связать их с проверяемыми деньгами по сумме и времени.` |
| предыдущий перевод не найден | `В доступной истории нет более раннего входящего перевода; часть денег могла находиться на кошельке раньше.` |

После причины бот добавляет: `Это ограничение данных, а не признак чистоты или
риска.` Эта оговорка не нужна, если тот же факт является доказанной сервисной
границей и уже объяснён в основном выводе.

Для реального кейса причина формулируется так:

```text
Оставшиеся 17% не удалось связать с входящими переводами: проверка достигла
лимита загрузки истории. Это техническое ограничение, а не отдельный признак
риска.
```

## Один механизм для любого score

AI-выжимка используется для любого валидного итогового score от `0` до `100`.
Score не выбирает готовый текст. Он задаёт тон и действие, а содержание
определяют факты конкретного кошелька.

### Низкий риск

Типичные факты: установленный источник с известной биржи, полное покрытие,
отсутствие существенных риск-сигналов.

```text
Проверяемая сумма пришла с Binance одним переводом. Посредников с повышенным
риском, связей с принудительным списанием USDT и блокировки токенов не найдено.

Происхождение всей проверяемой суммы установлено. Адрес можно принять
автоматически.
```

### Средний риск

Типичные факты: один bridge/DEX-маршрут без повторяемости, рискованный
контрагент как контекст, либо неполные данные без точного плохого сигнала.

```text
Часть суммы прошла через мост. Это может быть обычный обмен или перевод в
другую сеть. Повторяющегося транзитного маршрута и признаков кражи не найдено.

Источник 28% суммы не установлен: сервис данных не отдал старую историю.
Нужна ручная проверка, если сумма существенная.
```

### Высокий риск

Типичные факты: большая доля через один маршрут, повторяемость, быстрый вывод,
сохранение суммы или сильный source-policy сигнал без exact theft proof.

```text
Большая часть проверяемой суммы прошла через один мост в нескольких переводах.
Так может работать обычный обменный сервис, но повторяемый маршрут также
используют, чтобы скрыть происхождение денег.

Текущие данные не доказывают отмывание. Адрес нельзя принимать автоматически.
```

### Критический риск

Типичные факты: точная цепочка принудительного списания USDT, активная
блокировка USDT, подтверждённая санкционная метка или метка украденных средств.

```text
Адрес получил USDT после подтверждённого списания через approve и transferFrom.
Цепочка доказана транзакциями, указанными в отчёте.

Это точная связь с принудительным списанием USDT, а не предположение по
поведению кошелька. Депозит не принимать; материалы передать специалисту по
проверке рисков.
```

### Отдельные сценарии по фактам

Внутри каждого score AI выбирает только сценарии, которые разрешены найденными
фактами:

- `bridge / DEX / router`: обычный обмен или смена сети; при дополнительных
  сигналах — возможное сокрытие происхождения;
- `CEX`: вывод пользователя с биржи или сервисный кошелёк; после биржи нельзя
  связать публичные входы и выходы конкретного клиента;
- `operational / collector wallet`: кошелёк бизнеса, обменника или сборщик
  ликвидности; при быстром повторном выводе — возможный транзитный узел;
- `risky counterparty`: реальная связь с контрагентом, но не доказательство,
  что вся сумма имеет тот же риск;
- `GasFree fee`: комиссия сервиса или активация адреса; не доказательство
  смарт-контракта, кражи или грязного источника;
- `partial history`: техническое ограничение данных, не самостоятельный риск;
- `exact drain / blacklist`: точный факт без альтернативного смягчения.

Одинаковый score у двух кошельков может дать разный текст, потому что score —
это итоговая оценка, а объяснение строится из конкретных путей, сервисов,
адресов, переводов и ограничений.

## Утверждённый пример

Реальные данные для `TGytcHDm9k4r6QPvine8c6A3WWaqTBZAZD`:

- проверено 10 входящих переводов;
- прослежено 83% проверяемой суммы;
- все 10 найденных source paths связаны с `UsdtOFT`;
- адрес границы — `TFG4wBaDQ8sHWWP1ACeSGnoNR6RRzevLPt`;
- точных признаков кражи, принудительного списания USDT и блокировки токенов нет.

Ожидаемый финальный текст:

```text
Проверка адреса

TGytcHDm9k4r6QPvine8c6A3WWaqTBZAZD
🟠 78/100 — высокий риск. Не принимать автоматически.

Мы проверили 10 входящих переводов и проследили происхождение 83% суммы.
Все 10 переводов связаны с мостом UsdtOFT:
TFG4wBaDQ8sHWWP1ACeSGnoNR6RRzevLPt.

Это может быть обычный обмен или перевод активов в другую сеть. Такой же
маршрут используют, чтобы разорвать публично видимую цепочку происхождения
средств. Из-за большой доли и повторяемости адрес нужно проверить вручную;
текущие данные не доказывают отмывание.

Признаков кражи, принудительного списания USDT и блокировки токенов не найдено.
Оставшиеся 17% суммы не удалось связать с входящими переводами: проверка
достигла лимита загрузки истории. Это техническое ограничение, а не отдельный
признак риска.
```

LLM может менять порядок и формулировки, но не факты и доказательную силу.

## Контракт ответа LLM

LLM возвращает только JSON:

```json
{
  "paragraphs": [
    "Главная находка.",
    "Возможный смысл и ограничение."
  ],
  "usedEvidenceIds": ["source-1", "coverage-1"]
}
```

Требования:

- 2–3 абзаца;
- 250–700 знаков суммарно;
- одна мысль в предложении;
- сначала главная находка;
- только русский язык для `ru` locale;
- понятные слова для новичка;
- без HTML, Markdown, URL и заголовков внутри AI-части;
- без повторения score, решения и проверяемого адреса;
- без списков всех выполненных проверок;
- без внутренних кодов и названий режимов.

Индивидуальность создают факты конкретного кошелька, а не случайные эпитеты
или разный стиль ради разнообразия.

## Валидация ответа

AI-текст принимается только если:

- JSON соответствует схеме;
- `usedEvidenceIds` входят во входной case;
- каждый TRON-адрес входит в разрешённый список;
- каждое число и процент есть во входном case;
- текст не меняет score или decision;
- точные обвинения опираются на `proofStrength=exact`;
- упоминание возможного отмывания разрешено входными interpretations;
- обязательная оговорка присутствует;
- нет внутренних терминов;
- длина не превышает лимит;
- текст не повторяет одинаковую мысль.

Перед отправкой текст экранируется как Telegram HTML.

## Fallback

Fallback используется при таймауте, сетевой ошибке, неверном JSON или провале
валидации. Он строится из двух ведущих `NarrativeFact` и понятной строки о
покрытии.

Fallback не пытается воспроизвести свободный AI-текст. Его задача — быстро и
безопасно сообщить главные факты.

LLM-ошибка не меняет статус forensic job, score или решение и не задерживает
Telegram-ответ дольше отдельного короткого narrative timeout.

## Конфигурация

Используется существующий `LLM_API_KEY`, base URL, provider и model.

Для пользовательской выжимки нужен отдельный feature flag и короткий timeout.
DeepSeek thinking отключается: forensic-анализ уже завершён, модели нужно
только отредактировать готовые факты.

Новая модель, новая библиотека и отдельный provider не нужны.

## Хранение и приватность

В LLM-запрос не попадают:

- Telegram user id и chat id;
- имя пользователя;
- API-ключи;
- raw provider payload;
- внутренние stack traces;
- данные других проверок, не относящиеся к кошельку.

В первой версии narrative не требует новой таблицы и отдельного cache. LLM
вызывается один раз при доставке финального результата. Подробный
`/check_status <job-id> подробно` остаётся детерминированным.

## Ошибки и граничные случаи

- Нет финального score: LLM не вызывается.
- Нет существенных фактов: коротко написать, что сильных сигналов не найдено,
  и объяснить проверенную сумму.
- Есть hard evidence: показать его первым.
- Есть только поведенческий контекст: не называть его грязным происхождением.
- Есть несколько границ: выбрать границу, которая объясняет итоговый score;
  остальные оставить в подробном отчёте.
- DeepCheck и Where указывают разные адреса: не объединять их в один факт.
- Coverage неполное: назвать прослеженный и непрослеженный процент суммы.
- Coverage неполное: назвать техническую причину, почему остаток не прослежен.
- Coverage полное: не утверждать, что проверена вся жизнь кошелька; речь идёт
  о проверяемой сумме.

## Tests

Тесты используют fake LLM client и не делают платных сетевых запросов.

Минимальные сценарии:

1. Реальный bridge-кейс: 10 переводов, 83% суммы, UsdtOFT, обычный и рискованный
   сценарии, явное `не доказывает отмывание`.
2. Exact approval-drain: точный факт идёт первым и не смягчается.
3. ACCEPTABLE с чистым CEX-source: короткий спокойный вывод.
4. Behavior-only: нет обвинения в грязных средствах.
5. NO_FINAL_DECISION: ноль LLM-вызовов.
6. Preliminary: ноль LLM-вызовов и две строки статуса.
7. Финальный результат: ровно один LLM-вызов.
8. Неизвестный адрес в ответе: fallback.
9. Неизвестное число или процент: fallback.
10. Ссылка на несуществующий evidence id: fallback.
11. Заявление о краже без exact evidence: fallback.
12. Упоминание отмывания без разрешённой interpretation: fallback.
13. Упоминание отмывания без обязательной оговорки: fallback.
14. Таймаут, invalid JSON и текст длиннее 700 знаков: fallback.
15. Русская и английская локали сохраняют одни факты и числа.
16. Для каждого partial coverage reason есть понятное объяснение причины.
17. Один narrative writer покрывает LOW, MEDIUM, HIGH и CRITICAL без четырёх
    отдельных шаблонных отчётов.
18. GasFree fee объясняется как сервисная комиссия и не превращается в
    доказательство смарт-контракта или кражи.

## Implementation surface

Ожидаемые области изменений:

- новый небольшой модуль сборки `WalletNarrativeCase`, LLM prompt и validator;
- `src/llm/openAiCompatibleJsonClient.ts` — переиспользование существующего
  JSON-вызова;
- `src/index.ts` — создание narrative writer и один вызов перед финальной
  Telegram-доставкой;
- `src/bot/createBot.ts` — детерминированная шапка, preliminary и fallback;
- `src/config.ts` — отдельный feature flag и narrative timeout;
- focused unit tests и bot integration tests;
- `docs/knowledge/08-admin-and-bot-ux.md` и
  `docs/knowledge/09-current-decisions.md` — новый пользовательский контракт.

## Что не делаем

- не меняем scoring math;
- не меняем canonical decision;
- не просим LLM повторно расследовать кошелёк;
- не отправляем LLM полный raw report;
- не разрешаем LLM добавлять labels или доказательства;
- не меняем Admin UI;
- не меняем подробный support/debug отчёт;
- не добавляем новую зависимость или таблицу.

## Инфостиль

Пользовательский текст строится по схеме:

```text
факт -> возможный смысл -> граница знания
```

Убраны механические разделы, повторы, внутренние термины и общие выводы без
фактов. Каждое предложение сообщает факт, понятное объяснение или ограничение.

Утверждённый пример прошёл локальную инфостиль-проверку: чистота `100/100`,
читаемость `100/100`.

## Self-review checklist

- LLM не меняет score и решение.
- Факты и допустимые interpretations создаёт код.
- Возможное отмывание требует дополнительных сигналов и оговорки.
- Coverage объяснено через долю проверяемой суммы.
- Непрослеженная доля содержит конкретную техническую причину.
- Количество переводов не смешано с долей суммы.
- Один механизм покрывает любой валидный score.
- Другие сценарии выбираются по фактам, а не только по risk band.
- Текст рассчитан на новичка в криптовалюте.
- Preliminary и NO_FINAL не вызывают LLM.
- При ошибке есть детерминированный fallback.
- В LLM не уходят пользовательские и служебные данные.
- Подробный отчёт остаётся доступным.
- Новых зависимостей и таблиц нет.
- Объём укладывается в один implementation plan.
