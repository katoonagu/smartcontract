# Human summary для итоговых отчётов Telegram и Admin

Дата: 2026-07-09

Статус: утверждённый дизайн, перед implementation plan

Связанный инвентарь: `docs/superpowers/specs/2026-07-09-telegram-reason-copy-inventory.md`

## Задача

Сделать итоговый риск-отчёт понятным для человека.

Сейчас бот часто показывает технические причины: `source-policy`, `matrix row`, `hard-proof`, `coverage_partial`, raw scoring diagnostics.

Пользователь видит score, но не всегда понимает:

- что нашли;
- какой режим это нашёл;
- что это доказывает;
- чего это не доказывает;
- что делать дальше.

Нужен общий слой объяснения. Он не должен менять scoring math.

Он берёт готовые результаты FastCheck, Where Is Money, DeepCheck и unified score. Из них собирает человеческий отчёт.

## Решение

Делаем одну базу причин и две выдачи:

1. Обычный Telegram-отчёт.
2. Расширенный отчёт для админа и кнопки `Показать подробно`.

Обе выдачи строятся из одного `risk explanation summary`.

## Принципы текста

Пишем по правилу:

```text
факт -> смысл -> действие
```

Не пишем технический код без объяснения. Если термин нужен, рядом даём смысл.

Примеры замены:

| Было | Должно быть |
|---|---|
| `source-policy threshold reached` | `Источник выбранной суммы попадает под policy-риск. Это не доказывает кражу, но депозит нельзя принимать автоматически.` |
| `Scoring Signal Matrix winning row is hard_proof` | `Найдена точная причина высокого риска.` |
| `coverage_partial` | `Проверка относится к выбранной сумме и доступным данным, а не ко всей истории адреса.` |
| `Exact approval-drain provenance reaches checked wallet via 0 hop(s)` | `Найдена точная drainer-цепочка: approve USDT -> transferFrom -> проверяемый адрес получил средства.` |

В обычном Telegram не показываем:

- matrix rows;
- raw weights;
- dampener;
- run profile;
- provider budgets;
- internal evidence class;
- сырые коды.

Эти данные остаются в Admin/debug.

## Обычный Telegram-отчёт

Кому: обычному пользователю после финальной проверки.

Цель: за 20 секунд понять, можно ли принимать адрес, почему и что делать.

Структура:

```text
Проверка адреса - итог

Адрес: TNQdf...ZdDAC

Решение: не принимать автоматически.
Риск: 78/100 - высокий

Почему
• В выбранной сумме найден источник HTX/Huobi: 70%.
• Деньги дошли до биржи или сервиса. Дальше публичная трассировка ненадёжна.
• Точных признаков кражи, drainer-цепочки или USDT blacklist не нашли.

Что это может значить
Адрес похож на рабочий кошелёк. Он принимает USDT, собирает ликвидность и переводит деньги через биржи, bridge или DEX. Это не доказывает кражу, но источник денег попадает под policy-риск.

Что делать
• Не принимать депозит автоматически.
• Запросить подтверждение происхождения средств.
• Если сумма крупная - передать compliance.
```

Правила:

- максимум 5 причин;
- hard evidence всегда первым;
- source-risk идёт после hard evidence;
- поведение кошелька идёт как контекст, а не как доказательство;
- ограничения данных показываются отдельно;
- если hard evidence нет, явно пишем, чего не нашли.

## Расширенный отчёт

Кому: админ, аналитик, владелец продукта.

Где:

- Admin Analytics rail / Forensics summary;
- Telegram-кнопка или команда `Показать подробно` для админов.

Цель: показать всю картину по режимам без чтения raw JSON.

Структура:

```text
Расширенный отчёт по адресу

Адрес: TNQdf...ZdDAC
Итог: не принимать автоматически
Риск: 78/100 - высокий

Короткий вывод
Адрес нельзя принять автоматически. Главная причина - 70% выбранной суммы связано с HTX/Huobi. Точных доказательств кражи, approval-drain или USDT blacklist нет.

FastCheck
• Быстрых hard-сигналов не найдено.
• Поведение похоже на транзитный USDT-кошелёк.

Where Is Money
• Проверили выбранную сумму: 1 входящий USDT-перевод.
• 70% выбранной суммы пришло через HTX/Huobi.
• Цепочка дошла до биржи или сервиса.
• Exact approval-drain не найден.
• USDT blacklist не найден.

DeepCheck
• Адрес похож на операционный или ликвидный кошелёк.
• Есть движение через сервисы, bridge или DEX.
• Прямого доказательства грязного происхождения нет.

Что это может быть
• Рабочий кошелёк.
• Кошелёк для сбора ликвидности.
• Пользователь менял актив через bridge или DEX.
• Промежуточный транзитный кошелёк.

Ограничения
• После биржи или сервиса публичная цепочка обрывается.
• Это не доказывает кражу.
• Это не доказывает чистый источник.

Рекомендация
Не принимать автоматически. Запросить источник средств. Если сумма существенная - отправить на ручную проверку.
```

Правила:

- показываем режимы отдельно;
- показываем все существенные факты;
- показываем отрицательные факты: что не найдено;
- показываем доли, суммы, hop count, сервисы и даты санкций, если они есть;
- убираем дубли между разделами;
- не превращаем расширенный отчёт в scoring dump.

## Общий summary object

Добавляем общий сборщик, например:

```text
src/bot/riskExplanationSummary.ts
```

Он берёт:

- FastCheck `RiskReport`;
- Where Is Money `WhereIsMoneyReport`;
- DeepCheck `DeepAddressForensicReport`;
- unified wallet risk result;
- locale;
- режим вывода: обычный или расширенный.

На выходе:

```ts
type RiskExplanationSummary = {
  decision: "DECLINE" | "REVIEW" | "ACCEPTABLE" | "NO_FINAL_DECISION";
  score: number | null;
  level: RiskLevel | null;
  shortConclusion: string;
  primaryReasons: ExplanationFact[];
  modeSections: ExplanationModeSection[];
  possibleMeanings: string[];
  limitations: string[];
  recommendations: string[];
  absentEvidence: string[];
};
```

Пример факта:

```ts
type ExplanationFact = {
  kind:
    | "hard_evidence"
    | "source_risk"
    | "behavior_context"
    | "coverage_limit"
    | "absent_evidence";
  source: "fast" | "where" | "deep" | "unified";
  priority: number;
  textRu: string;
  textEn: string;
  detailRu?: string;
  detailEn?: string;
  actionRu?: string;
  actionEn?: string;
  dedupeKey: string;
};
```

Сборщик не считает риск. Он только объясняет уже посчитанный риск.

## Факты из FastCheck

FastCheck отвечает: есть ли быстрый очевидный риск.

Показываем:

- сохранённый exact approval-drain сигнал;
- active USDT blacklist;
- внутреннюю scam / phishing / stolen funds метку;
- отсутствие быстрых hard-сигналов;
- транзитное поведение, если оно есть.

Формулировки:

```text
Ранее система уже находила для этого адреса точную drainer-цепочку.
Адрес находится в активном USDT blacklist.
Быстрых hard-сигналов не найдено.
Поведение похоже на транзитный USDT-кошелёк.
```

Не показываем:

```text
internal_label_approval_drain_proximity
raw 80
fast_context
```

## Факты из Where Is Money

Where Is Money отвечает: откуда пришли выбранные деньги.

Показываем:

- что именно проверили: выбранная сумма, recent-flow anchor, drain episode;
- сколько входящих USDT-переводов вошло в проверку;
- доли источников: HTX/Huobi, WhiteBIT, bridge/router/DEX, unknown contract, risky label;
- service boundary;
- exact approval-drain;
- санкционный сервис с authority и датой;
- clean CEX not fully proven;
- materiality caveat;
- coverage limit.

Формулировки:

```text
Проверили выбранную сумму: 5 входящих USDT-переводов.
70% выбранной суммы пришло через HTX/Huobi.
Цепочка дошла до биржи или сервиса. Дальше публичная трассировка ненадёжна.
Чистый CEX-источник не доказан полностью.
Часть происхождения осталась ниже materiality-порога.
```

Если есть санкционный сервис:

```text
Цепочка дошла до санкционного криптосервиса <service>. Орган: <authority>. Дата включения: <date>.
```

Если HTX/Huobi до санкционной даты:

```text
Источник связан с HTX/Huobi, но событие относится к периоду до санкционной даты. Это обычный source-risk, не санкционный hard proof.
```

## Факты из DeepCheck

DeepCheck отвечает: на что похож адрес и его окружение.

Показываем:

- операционный кошелёк;
- collector / liquidity wallet;
- transit wallet;
- движение через сервисы, bridge, DEX, router;
- рискованного крупного контрагента;
- drainer-связь через N hop;
- blacklist или exact hard evidence, если нашёл DeepCheck;
- отсутствие точного плохого доказательства.

Формулировки:

```text
Адрес похож на операционный или ликвидный кошелёк.
Адрес получает средства от нескольких отправителей и концентрирует их перед дальнейшим переводом.
Адрес быстро переводит большую часть входящих USDT дальше.
Крупный контрагент адреса сам выглядит рискованно.
Точных доказательств грязного происхождения DeepCheck не нашёл.
```

## Отрицательные факты

Отчёт должен показывать не только что найдено, но и чего не найдено.

Примеры:

```text
USDT blacklist не найден.
Exact approval-drain цепочка не найдена.
Прямой scam-label не найден.
Точных доказательств кражи не найдено.
Чистый источник не доказан.
```

Это защищает отчёт от перекоса. Пользователь видит разницу между:

- нашли плохое;
- не смогли доказать чистое;
- данных не хватает.

## Словарь причин

### HTX/Huobi

Обычный отчёт:

```text
В выбранной сумме найден источник HTX/Huobi: <percent>.
```

Расширенный отчёт:

```text
<percent> выбранной суммы пришло через HTX/Huobi. Это риск по источнику средств. Сам по себе он не доказывает кражу или drainer-цепочку.
```

Историческая связь:

```text
У адреса была историческая связь с HTX/Huobi. Это контекст, но не доказательство происхождения выбранной суммы.
```

### Bridge / DEX / router

Обычный отчёт:

```text
Часть выбранной суммы прошла через bridge, DEX или router.
```

Расширенный отчёт:

```text
Цепочка дошла до bridge, DEX или router. После таких сервисов публичная трассировка становится менее надёжной: адрес мог просто обменять актив или перевести его в другую сеть.
```

### Сервисная граница

```text
Деньги дошли до биржи или сервиса. Дальше публичная трассировка ненадёжна.
```

Расширенно:

```text
Цепочка остановилась на бирже или сервисе. После такой точки нельзя точно связать дальнейшие входы и выходы только по публичной блокчейн-истории.
```

### Exact approval-drain

```text
Найдена точная drainer-цепочка: approve USDT -> transferFrom -> получатель средств.
```

Расширенно:

```text
Система нашла точную цепочку approval-drain. Сначала владелец дал approve на USDT, затем токены списали через transferFrom, после этого средства дошли до проверяемого адреса.
```

Через несколько шагов:

```text
Средства дошли до проверяемого адреса через <N> hop после первого получателя.
```

### Saved approval-drain marker

```text
Ранее система уже находила для этого адреса точную drainer-цепочку.
```

Расширенно:

```text
В базе есть сохранённый hard-сигнал по этому адресу: раньше система находила цепочку approve -> transferFrom -> получатель средств.
```

### USDT blacklist

```text
Адрес находится в активном USDT blacklist.
```

Расширенно:

```text
Официальный TRON USDT контракт показывает, что адрес заблокирован. Это точное состояние контракта, не поведенческая оценка.
```

### Санкционный сервис

```text
Цепочка дошла до санкционного криптосервиса: <service>.
```

Расширенно:

```text
Цепочка дошла до санкционного криптосервиса <service>. Орган: <authority>. Дата включения: <date>. Это санкционный риск по источнику средств.
```

Оговорка:

```text
Это не доказывает кражу, но по policy такой источник нельзя принимать автоматически.
```

### Операционный кошелёк

```text
Адрес похож на рабочий кошелёк: принимает USDT и быстро переводит дальше.
```

Расширенно:

```text
Адрес похож на operational wallet. Он принимает USDT, собирает ликвидность и переводит средства дальше через биржи, сервисы, bridge или DEX.
```

Оговорка:

```text
Так могут работать нормальные кошельки бизнеса, трейдера или обменника. Само по себе это не доказывает грязное происхождение.
```

### Collector / liquidity wallet

```text
Адрес похож на кошелёк для сбора ликвидности.
```

Расширенно:

```text
Адрес получает средства от нескольких отправителей и концентрирует их перед дальнейшим переводом. Это похоже на collector или liquidity wallet.
```

### Transit wallet

```text
Адрес похож на транзитный кошелёк.
```

Расширенно:

```text
Адрес быстро переводит большую часть входящих USDT дальше. Это похоже на транзитный кошелёк. Такой паттерн бывает у нормальных сервисов и у цепочек отмывания.
```

### Рискованный контрагент

```text
Крупный контрагент адреса сам выглядит рискованно.
```

Расширенно:

```text
Часть входящего или исходящего объёма связана с контрагентом с высоким быстрым риском. Это повышает приоритет ручной проверки, но не доказывает происхождение выбранной суммы.
```

### Чистый CEX не доказан

```text
Чистый источник с биржи не доказан полностью.
```

Расширенно:

```text
Мы видим признаки биржи или сервисной границы. При этом мы не можем доказать, что выбранная сумма пришла из чистого CEX-источника.
```

### Неполное покрытие

```text
Проверили не всю историю адреса. Итог относится только к выбранной сумме и доступным данным.
```

Расширенно:

```text
Покрытие неполное: часть истории или часть происхождения не попала в проверку. Это ограничение данных, а не самостоятельное доказательство риска.
```

## Решения и рекомендации

### DECLINE

Когда:

- hard evidence;
- санкционный сервис;
- сильный source-risk;
- высокий HTX/Huobi share;
- точная drainer-цепочка;
- USDT blacklist.

Текст:

```text
Решение: не принимать автоматически.
```

Рекомендации:

```text
• Не принимать депозит автоматически.
• Запросить подтверждение происхождения средств.
• Если сумма крупная - передать compliance.
```

Если hard evidence:

```text
• Не принимать депозит.
• Не перемещать средства без решения compliance.
• Сохранить отчёт и доказательства: адреса, tx hash, цепочку.
```

### REVIEW

Когда:

- средний source-risk;
- bridge/DEX контекст;
- операционный кошелёк без точного плохого доказательства;
- неполное покрытие;
- крупный рискованный контрагент.

Текст:

```text
Решение: нужна ручная проверка.
```

Рекомендации:

```text
• Не принимать автоматически, если сумма существенная.
• Запросить подтверждение происхождения средств.
• Проверить, совпадает ли объяснение клиента с цепочкой переводов.
```

### ACCEPTABLE

Когда:

- сильных риск-сигналов нет;
- покрытие достаточно;
- hard evidence нет;
- source-risk не найден.

Текст:

```text
Решение: можно принять автоматически.
```

Оговорка:

```text
Проверка относится к выбранной сумме и доступным данным, а не ко всей истории адреса.
```

### NO_FINAL_DECISION

Когда:

- не хватает данных;
- история не загружена;
- provider cap;
- technical stop.

Текст:

```text
Решение: финальный риск не опубликован.
Причина: не хватает данных по происхождению средств.
```

Не показываем пользователю:

```text
NO_FINAL_DECISION
provider_cap_unresolved
History not fully fetched
```

Рекомендации:

```text
• Дождаться индексации истории.
• Перезапустить проверку после загрузки данных.
• Не считать адрес чистым или грязным до финального результата.
```

## Что это может быть

Этот блок не оправдывает адрес. Он объясняет похожие сценарии.

Варианты выбираются только из найденных фактов.

Обычные варианты:

```text
• Рабочий кошелёк бизнеса или обменника.
• Кошелёк для сбора ликвидности.
• Перевод после обмена через bridge или DEX.
• Промежуточный транзитный кошелёк.
```

Если есть drainer:

```text
• Адрес получил средства из drainer-цепочки.
• Адрес может быть промежуточным получателем после списания USDT.
```

Если есть blacklist:

```text
• Адрес уже заблокирован на уровне USDT-контракта.
```

Если данных мало:

```text
Данных недостаточно, чтобы объяснить происхождение средств. Нужно дождаться покрытия.
```

## Implementation outline

1. Добавить `riskExplanationSummary.ts`.
2. Перенести туда сбор фактов из текущих reason cards и report helpers.
3. Оставить scoring без изменений.
4. Переписать обычный `formatUnifiedAddressFinalReport` так, чтобы он читал summary.
5. Добавить extended formatter.
6. Подключить extended formatter в Admin Analytics rail / Forensics summary.
7. Добавить Telegram admin-действие `Показать подробно` или отдельную команду, если в текущей кнопочной модели это проще.
8. Оставить beta/internal diagnostics только для debug/support режима.

## Tests

Минимальные сценарии:

1. Exact approval-drain 95:
   - обычный отчёт первым пишет drainer-цепочку;
   - поведение не объясняет score;
   - extended показывает Fast/Where/Deep отдельно.

2. HTX/Huobi 70%:
   - обычный отчёт пишет источник HTX/Huobi и рекомендацию не принимать автоматически;
   - extended показывает долю и сервисную границу.

3. Bridge/DEX без hard evidence:
   - обычный отчёт пишет, что это может быть обычный обмен;
   - decision не звучит как кража.

4. Operational wallet / behavior only:
   - обычный отчёт не пугает;
   - пишет, что это контекст;
   - extended показывает роль кошелька.

5. No hard evidence + partial coverage:
   - отчёт пишет ограничения данных;
   - не говорит, что адрес чистый.

6. NO_FINAL_DECISION:
   - нет `provider_cap_unresolved` в обычном тексте;
   - есть понятное `не хватает данных`.

7. Санкционный сервис:
   - после даты санкций пишет санкционный сервис;
   - до даты санкций не превращает историческую HTX-связь в санкционный hard proof.
